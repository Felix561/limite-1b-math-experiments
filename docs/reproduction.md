# Reproduction details

FULL marks a complete run at the native token budget (as opposed to a reduced PILOT).

## AIME 2026 (FULL, avg@32, 2026-10-26)

**`exact` (MathArena's published grader, the paper's headline column) = 92.40 % avg@32, 95 % CI 84.3–98.1 %**
(percentile bootstrap over the 30 problems). The technical report gives 94.01 % (Table 5), which lies inside the
interval; the point estimate is 1.61 pp lower. All numbers: `results/reproduction/aime26.json`.

Per-problem `exact` (%, problems 1–30): 100 ×8, 93.8, 71.9, 96.9, 100 ×3, **0.0** (P15, 0/32), 100, 96.9, 100 ×4,
96.9, 100 ×2, 87.5, 100 ×2, 56.2, 90.6, 81.2.

**Protocol.** The run uses upstream [`limite-violetto`](https://github.com/paradigma-inc/limite-violetto) at
`7ddad34`, with `cd limite-evals && uv sync --locked` (uv 0.13.5) and then
`uv run --locked limite-eval paradigma-inc/limite-1b-violetto --tasksets aime26`, all other settings at the harness
defaults:
- the checkpoint pin `b1f3d572` from the harness allowlist and the chat profile;
- temperature 0.6, top_p 0.95, 32 rollouts;
- base seed 0 (the rollout seed is problem × 32 + rollout and does not depend on other tasksets, so the run is
  identical to a full-suite run);
- a native budget of 126,976 tokens, client concurrency 320 and bf16;
- vLLM 0.28.0+cu129, torch 2.13.0+cu130, transformers 5.14.1 and Python 3.12.3;
- the dataset `MathArena/aime_2026` at the harness pin and the grader `eth-sri/matharena@a11194d`.

Script: `gpu/aime26_reproduction.sh`. A one-problem pilot (`--limit 1`) came first, as a plumbing check only.

**Differences from the model card.**
- Only `--tasksets aime26` was scored, not the whole `math-extended` suite.
- The hardware was one A100-SXM4-40GB (sm_80), not the H100 the model card validates. Upstream's protocol states
  that another compatible accelerator changes throughput, not the measurement contract.
- On hosted notebooks, kernel variables (`PYTHONPATH`, `MPLBACKEND`) leak into Python and shadow the locked venv.
  `gpu/setup.sh` clears them, so the host matches a clean machine.

**Cost.** The run generated 29.1M tokens across the 960 rollouts. The full run took 267 min on the A100-40GB:
- Generation throughput averaged 1.82k tok/s. It started at 4.2k tok/s and then became KV-bound: the KV cache sat at
  99–100 %, with at most 256 running sequences and 5,013 preemptions.
- Peak VRAM was 38.6 GiB.

**Reading the 1.6 pp gap.** Within-problem sampling noise of one avg@32 run is ~0.57 pp (binomial over 32 rollouts
per problem). The paper's 94.01 % is itself one such estimate, so the difference of two runs has an SE of ~0.8 pp
and the gap is ~2 SE. That is borderline and consistent with seed noise plus at most a small systematic shift.
Two explanations are possible; neither was tested:
- Hardware numerics differ (A100 vs H100 kernels; preemption and recomputation under KV pressure; continuous
  batching is not bitwise reproducible anyway).
- The reported figure may come from a different sample count or aggregation: 94.01 % lies between 902/960
  (93.96 %) and 903/960 (94.06 %), so it is not a correct/960 count at 32 samples per problem. Our count is 887/960.

## HMMT Feb 2026 (FULL, avg@24, 2026-10-31)

**`exact` = 81.19 % avg@24, 95 % CI 70.3–90.7 %** over the 33 problems. The paper gives 83.62 % (Table 5), inside the
interval. Mean completion length is 45.1k tokens.

The samples were generated by `scripts/value_study.py gen`, because the value-model study needs every sample's token
ids. That script follows the harness protocol:
- the same pinned checkpoint, through the harness's own `hmmt26` taskset loader and prompt rendering;
- the chat profile (temperature 0.6, top_p 0.95), seeds problem × 32 + rollout and the native 126,976-token budget;
- the harness's own graders.

The run used 24 instead of 32 samples per problem, a compute decision made before any data
(`docs/preregistration.md`). It ran as two jobs, problems 0–16 and 17–32, on one RTX PRO 6000 Blackwell each. The
per-problem accuracies are in `results/value_model/analysis.json` (`hmmt26_baseline`).
